工具和 Skills 很多时，
Codex 与 Claude Code 怎样处理？

是渐进式披露，但不是只给 Skill 做一个目录。两者把「发现 Skill」「读取 Skill 操作说明」「发现具体 Tool」「加载完整 Tool schema」分开。大量能力可以已安装、已鉴权、已启用，但不必在每一次模型请求里全部展开。

前篇：腾讯智能表 34,925 字节工具定义拆解。本篇为官方文档与公开源码调研，不是对两款 CLI 的实机性能测试，也没有修改 Mochi 的运行行为。

01 · 先把四种东西分开

层次内容应该何时进入模型上下文？
能力目录有哪些服务、Skill 名称、简短用途、能力边界。小型入口可常驻；目录本身也要有预算。
Skill 操作说明如何完成一类任务，流程、约束、参考文件。Skill 被选中时加载，不要全部放在系统提示词里。
工具定义函数名、参数类型、必填项、嵌套 schema。发现相关工具后，选择性提供完整定义。
工具执行与权限实际发请求、写数据、访问凭据。模型发出明确调用后，由宿主校验并执行；发现能力不等于获得权限。

MCP 的 tools/list 是宿主获取工具目录的协议操作；目录已缓存在宿主，不代表所有 schema 必须发给模型。模型侧的按需披露需要 Agent 宿主和模型 API 共同配合，不能指望「接入 MCP」就自动解决。

02 · Skill 的渐进式披露：两者基本一致

1 / 先知道能做什么

只列 Skill 名称、简短描述和定位信息。模型根据任务选择，而不是先读全部操作手册。

2 / 选中后读 SKILL.md

加载该 Skill 的操作流程、边界、注意事项、参考资料入口。

3 / 再按需读辅助资源

需要哪一项，才读 references 中的文档或执行相应脚本。不会因为选中 Skill 就把整套资料塞入上下文。

Codex 随仓库提供的 skill-creator 指南明确列出这三个阶段。Claude Code 的 Skills 文档也强调正文仅在调用时加载，详细 API 说明和示例应移入 supporting files。[1][4]

目录也不是零成本

Claude Code 当前文档将 Skill 列表预算按模型上下文窗口的 1% 缩放，预算以字符处理；超出时保留名称，从低调用频率 Skill 开始移除描述。单条描述与 when_to_use 合并文本默认最多 1,536 字符，可配置。[1]

本次核验的 Codex render.rs 使用另一组规则：默认按已知上下文窗口的 2% 计算 metadata token 预算；未知窗口时退回 8,000 字符预算；单条目录描述上限 1,024 字符。显式配置的 metadata token 预算另有限制。这些是源码快照里的实现细节，不是 Agent Skills 标准的统一规定。[9]

已加载的 Skill 不会自动变成零成本

Claude Code 文档说明：调用后，Skill 内容作为消息留在后续上下文中；相同内容再次调用时可避免重复注入。context: fork 可让 Skill 在独立子代理上下文运行，但不是每个 Skill 默认都会创建子代理。[1]

disable-model-invocation: true 让用户控制触发时机，并不把 Skill 的操作权限授予模型；user-invocable: false 则是另一回事：不作为用户命令暴露，但仍可由模型使用。[1]

03 · Claude Code：ToolSearch + 延迟定义

官方产品文档已核验 开启工具搜索时，启动阶段主要提供工具名称及服务说明，不预先把全部 MCP 参数 schema 放进模型上下文。模型需要某项能力时，调用 ToolSearch，再加载相关定义。服务级说明因此很重要：它告诉模型「何时值得搜索这个服务」。[2]

大量 MCP 工具保存在宿主目录
        ↓
模型先看到轻量入口：名称、服务用途、ToolSearch
        ↓
搜索相关能力 → 加载选中的工具定义 → 发出真实工具调用

重要更正：10% 不是当前唯一的默认行为

检索结果中仍有旧文章说「MCP 工具超过上下文 10% 才自动开启」。但本次读到的官方当前文档是：

ENABLE_TOOL_SEARCH当前文档规则
未设置 / true兼容模型和部署下，MCP 工具默认延迟加载。
auto阈值模式：候选定义总量不足上下文 10% 时提前加载；达到阈值后开启工具搜索。
auto:N自定义百分比，例如 auto:5。
false不延迟，全部提前加载。

可通过服务配置 alwaysLoad 或工具 _meta["anthropic/alwaysLoad"] 控制特定工具的加载策略。适合常驻的应是少量高频基础工具，而不是整个大型企业服务。[2]

它也做文本限额，但不是把全部参数 schema 随便截断

当前文档对服务说明/提前加载工具描述设 4,096 字符限制，对搜索后加载的工具描述设 16,384 字符限制。这针对的是描述字段和服务说明；不能把它理解为整个 inputSchema 都会自动压成 4 KB。腾讯智能表的大头在嵌套参数说明与结构，仍需要按需工具披露。[2]

兼容性与回退

工具搜索依赖模型/服务端支持。Claude Code 文档明确指出，一些 Microsoft Foundry 的 Azure 托管部署会拒绝所需字段并回退为提前加载；网关也需要转发 defer_loading、tool_reference 及相应协议头。这说的是 Claude Code 的部署兼容性，不能推导出 Azure OpenAI 某个部署一定支持或一定不支持 Codex 的工具搜索。[2]

04 · Codex：源码里能看到的完整链路

公开源码已核验 本节固定到 openai/codex@ee344ca9458351a6ea102795fa73110ad3ede5dc。它反映该源码快照，不声称所有历史版本、第三方网关或已安装二进制都有相同行为。

  1. 注册但延迟暴露。spec_plan.rs 把 model_info.supports_search_tool 传入 MCP 注册；mcp_tool_exposure.rs 根据它选择 ToolExposure::Deferred 或 Direct。因此工具可以已经在本地注册，但尚未直接给模型。[5][6]
  2. 给模型一个发现入口。tool_search_spec.rs 声明 tool_search，使用 execution: "client"，参数为 query 和可选 limit；本次源码默认返回数量为 8。工具说明明确说匹配结果提供给下一次模型调用。[7][10]
  3. 客户端检索。ToolSearchHandler 只为 deferred 项建立检索目录，在元数据语料上使用 BM25 排序；会缓存索引，并在工具来源变化时更新。它不是每次都让模型先阅读全部 schema 再挑选。[8]
  4. 只实体化被选中的工具。搜索结果转换为可加载工具定义，通过专用 ToolSearchOutput 响应项继续交给模型；不是只返回一段工具名称、让模型猜参数。[11]
  5. 受模型能力和工具策略约束。规划器还检查工具搜索是否被策略允许、是否存在可搜索的 deferred 工具。与 Code Mode 结合的分支另有功能条件，不能把它和普通工具搜索混为一谈。[5]

仓库内有 search_tool_enabled_by_default_adds_tool_search 和 small_app_tool_sets_are_deferred_by_default 测试，后者验证小型 App 工具集也可默认延迟，而非必须攒到很多工具才启用。这里核验的是测试源代码，没有在本机运行 Codex 上游测试。[10]

实现启发：BM25 不需要为了工具检索额外调用一个大模型，但该源码路径使用 English 分词配置。Mochi 以中文输入为主，不能原样照搬分词和查询假设；要验证中文名称、别名、功能描述及跨语言查询的召回率。

05 · Mochi 不是完全没有渐进式披露

层次当前代码结论
Skill 发现AgentPromptBuilder.appendSkillCatalog 先写名称、描述与位置。已有轻量目录，但数量上限不等于 token/字节预算。
Skill 正文LoadSkillTool 在调用时读取完整 Skill 文档。已经按需加载。
Tool schema普通模型轮次直接使用 activeToolRegistry.schemas。仍会发出整套活动工具定义。
Responses 编码ResponsesAdapter 遍历请求内全部工具，并编码为 function 定义。没有自动变成搜索式、按需注入。

所以，把更多说明搬进 Skill，并不会自动阻止 35 KB 的腾讯智能表 schema 出现在购物请求里。必须将「全局已启用工具」与「本轮模型可见工具」分开。当前代码证据见 [12]。

06 · 对 Mochi 最值得借鉴的方案

建议设计 · 尚未实现 优先实现宿主控制的两级目录，而不是盲目删工具、扩大超时时间，或直接把 API 特殊字段塞进现有适配器。

常驻层

少量基础工具、Skill 简介、能力分类、一个轻量工具发现入口。

发现层

按任务在已授权工具中搜索。返回候选用途/名称，并由宿主激活相关完整 schema。

执行层

下一轮只发当前已加载工具。仍用原始 schema 校验参数、权限和连接状态，再执行。

先用普通 function tool 实现，不假设 Azure 支持专用协议

例如新增概念上的 discover_tools(query)：本地检索后更新该运行的可见工具集合，下一轮再发送选中 schema。这样无需先依赖 Codex 的专用 tool_search_output，也无需冒充 Claude 的 defer_loading 协议。是否使用模型原生工具搜索，应在相应 Provider 的兼容性测试通过后再决定。

购物任务应该怎样流转？

用户：查找商品并加入购物车
  → 看到浏览器/购物相关能力入口
  → 发现并加载所需浏览器工具，必要时加载相关 Skill
  → 搜索、核实、执行用户授权的操作
  → 本次没有智能表编辑需求，不加载 smartsheet.add_fields

只有任务真的需要新增表格字段时
  → 查找腾讯智能表能力
  → 加载该工具完整定义和必要的 Skill 说明
  → 校验准确参数后再执行

必须保留的工程约束

  • 权限与可见性分离：发现不提升权限；关闭连接、撤销工具后，缓存结果不得继续调用。
  • Skill 就绪与 schema 已加载分离：启用条件基于已授权可用能力，不能因为工具尚未披露就误判 Skill 不可用。
  • 有明确预算：目录和已加载 schema 都按字节/token 管理；数量相同的工具可能相差几十倍，不能只限制“最多几个”。
  • 保留契约：不要为了凑预算截断 JSON、删除必填约束或裁掉关键错误说明；超预算应明确返回可操作的发现/缩小范围提示。
  • 避免越用越膨胀：同一运行去重已加载定义，保持版本/调用关联一致；运行结束后不要无条件把全部发现结果带入下一任务。
  • 检索不能成为新障碍：支持精确名称、分类、中文别名和低召回时继续发现；不应只凭一个关键词永久屏蔽其他工具。
  • 衡量完整链路：增加一次发现调用会有成本，应同时比较首个有用结果时间、总轮次、请求/回包大小、失败率和工具选择准确性。

需要解决的是「把不相关的完整契约提前发给模型」，而不是把能力本身删除。渐进式披露不能修复 TCP 建连抖动，但能减少无关 token、上传数据和被 Responses 回显的工具定义，降低完整请求撞上 20 秒预算的风险。
