需要约 35 KB 的定义？

不是工具名字或一句说明很长，而是把 24 种列类型的完整参数说明，以及公式、查找引用的嵌套格式设置，全部一次性交给模型。其中大量说明和类型配置重复展开。对一个购物请求来说，这些表格编辑细节完全没有必要提前出现。

01 · 35 KB 到底花在哪里？

工具最外层的英文说明只有 53 个 UTF-8 字节（加 JSON 引号为 55 字节）。真正的大头是 parameters.fields.items 中的各类列属性。

说明字段占比和子树占比是两种不同切法，存在交叉，不能相加。删除说明的结果只是体积分析，不是建议直接删除这些约束。

02 · 膨胀来自「多类型全集 + 嵌套重复」

它不是一个仅接收「列名」的简单工具，而是一个能创建多种复杂列的通用接口。即使用户只要新增一列文本，模型也会先收到公式、货币、日期、查找引用、关联记录等完整定义。

普通字段配置fields.items.properties

展开数字、货币、日期、成员、多选等 property_* 结构。

公式结果格式property_formula.formatter

为了描述公式结果怎样显示，再展开一组类似属性。仅 formatter 就有 9,201 B。

查找结果格式property_lookup.formatter

查找结果同样需要展示格式，再展开一次。该 formatter 为 9,057 B。

例如 currency_type 的货币枚举说明、日期格式说明、数字精度说明，会在普通列、公式格式和查找格式中重复出现。三个 formatter 并非字节级完全相同，不能直接把其中一份删掉。

一共出现 223 个 description，但只有 121 种不同文本；重复出现的说明有 102 处。模型不仅要接收 JSON 结构，还要阅读大量同义的使用规则。

中文通常每个汉字占 3 个 UTF-8 字节；但 字节数不是 token 数。不能把这里的 34,925 B 当成 34,925 tokens，也不能把整个请求的 27,090 tokens 都算在这个工具上。

04 · 它怎样放大了这次超时风险？

单个工具约占当次 135 KB 请求的 25.8%。问题不在于它执行慢：发生超时的第一轮还没有调用任何工具，而是模型请求提前携带了全部 77 个工具定义。

Azure Responses 的返回对象还带有 tools 字段，回显工具定义。成功样本中，该字段压成紧凑 JSON 仍有 130,734 B；实际 output 仅 309 B，没有加密推理内容。原始回包还包含空白格式和其他元数据，所以总量达到约 249 KB。

另外复现了 TCP 建连耗时约 15.5 秒，以及已经收到 HTTP 200、但响应正文在第 20 秒仍未下载完成的情况。网络抖动与大回包叠加，可以解释服务端成功而手机超时；不能把全部责任归于这个单独工具。

5 个工具仅用于隔离体积因素，不代表已经具备完成购物任务所需的能力。以上不是网络稳定性的长期统计，也不是证明所有 77 工具请求必然超时。

05 · 更合适的处理方式

  1. 先发现能力，再加载完整工具定义。购物阶段只需相关的浏览器、搜索或购物能力，不应预先加载腾讯智能表新增字段的全部参数。
  2. Skill 与 Tool 分开做渐进式披露。Skill 先暴露名称和用途，选中后读完整操作说明；Tool 先提供可检索的能力目录，选中后再给模型完整 schema。
  3. 完整校验契约保留在本地。不要通过截断 schema、删除必填项或丢弃错误约束来压缩请求；模型看到的简化入口也必须有可靠的参数验证与精确定向。
  4. 谨慎评估结构去重。$defs/$ref、拆分按列类型的工具、精简重复说明可能进一步减重，但必须验证所用模型 API 的 schema 兼容性；它们不是零风险的自动替换。

本报告只解释现状及优化方向：没有调整工具开关、没有缩短真实 schema、没有修改 20 秒限制，也没有执行任何智能表写操作。
